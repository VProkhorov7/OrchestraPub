# Память проекта: wiki, факты, решения, журнал

[English](MEMORY.en.md) · **Русский**

С версии 0.6 у каждого репозитория может быть своя память. Она живёт в самом репозитории и уходит в git вместе с кодом, поэтому одинаково доступна на Mac mini, на MacBook через Orca, в любом ИИ-агенте и в Orchestra.

## Из чего она состоит

| Где | Для кого | Что внутри |
|---|---|---|
| `wiki/` | для людей | Описание проекта: как устроено, как запускать, как деплоить. Обновляется вместе с изменениями кода. |
| `wiki/JOURNAL.md` | для вас | Журнал микросессий: коротко и по-русски, что сделано, почему и что дальше. Новые записи сверху. |
| `CHANGELOG.md` | для людей | Выжимка по этапам в формате Keep a Changelog: Added, Changed, Fixed, Security, Removed. |
| `.memory/facts.json` | для ИИ | База фактов: что уже выяснено (`F-0001` и дальше), с тегами и файлами. |
| `.memory/logic.json` | для ИИ | База логики: решения (`D-0001`…), почему именно так, что отвергли и какие последствия. Новое решение может заменить старое (supersedes). |
| `.memory/log/ГГГГ-ММ.jsonl` | для ИИ | Подробный лог всех действий: дата, тип, автор, файлы, описание, детали. |
| `.memory/config.json` | настройки | Папка wiki, длительность микросессии (35 минут), строгий режим. |

Если в проекте уже есть папка `wiki`, `Wiki`, `docs/wiki` или `docs`, память использует её, а не создаёт новую.

## Как это работает

**Перед задачей.** Агент смотрит в память: что по этой теме уже найдено и сделано (факты, лог), а затем почему сделано именно так (решения). В Claude Code это происходит само: хук на каждое сообщение подмешивает подходящие факты и решения. Orchestra добавляет память в задание оркестратору, планировщику и каждому воркеру.

**Во время работы.** Каждое изменение файла и значимая команда попадают в JSON-лог. Новые факты и решения агент записывает сам (`add-fact`, `add-decision`).

**Микросессия (30–40 минут).** Когда время подходит, агент получает напоминание и закрывает сессию: одна команда создаёт две записи: понятную людям в `wiki/JOURNAL.md` и подробную в `.memory/log/`. Если сессия не закрыта, её закроет хук конца сессии Claude Code или ближайший коммит, и запись будет помечена как автоматическая. Запуск Orchestra тоже считается микросессией: итоговый отчёт оркестратора становится записью в журнале.

**Коммит и push.** Git-хук `pre-commit` добавляет в каждый коммит `.memory/`, `wiki/` и `CHANGELOG.md` и пишет событие «коммит» в лог. Если перед `git push` осталась несохранённая память, хук `pre-push` оформит её отдельным коммитом и попросит повторить push. Команда `orchestra-memory push` делает всё за один раз. Это работает из терминала, из Orca, из любого GUI-клиента git: хуки лежат в репозитории (`.githooks/`).

**Wiki.** Если код изменился, а wiki нет, при закрытии сессии и при коммите появляется предупреждение. В строгом режиме (`"requireWiki": true` в `.memory/config.json`) такой коммит не пройдёт.

**Выжимки.** «Дай свежую выжимку» агенту в Claude Code или кнопка «Свежая выжимка» в Orchestra кратко пересказывают последние записи лога. В конце этапа кнопка «CHANGELOG этапа» (или `orchestra-memory changelog --draft`, затем `--write`) собирает из лога записи для `CHANGELOG.md` без мелких технических деталей. Orchestra делает это самой дешёвой рабочей моделью; без неё выжимка собирается из лога как есть.

## Команда /orchestra

`init` ставит в проект команду Claude Code `/orchestra` (`.claude/commands/orchestra.md`). Она задаёт порядок постановки задачи: память проекта → бриф (цель, границы, подзадачи, критерии готовности, проверка) → ваше утверждение → выполнение через Orchestra (раздать исполнителям или автопилот) или самим Claude → отчёт и запись в память. Если в проекте уже есть свой файл с таким именем, он не трогается.

## Защита и порядок (с версии 0.7.1)

Приёмы из практики коллег и проекта Skaro, они встроены как механизмы, а не как правила в тексте:

| Что | Как работает | Что делает владелец |
|---|---|---|
| **Сторож прода** | Хук перед каждой командой агента останавливает `wrangler deploy`, команды с `--remote`, `wrangler secret put`, запись в боевые KV/R2, `npm run deploy`, `gh workflow run`, принудительный push и — где push в `main` выкладывает сайт (site-b) — push в `main`. Агент объясняет, что сделает команда, и просит разрешения. Исполнителям Orchestra прод недоступен никогда: у них нет ключей Cloudflare и GitHub, и сторож их не пускает даже при разрешении | Пишет «разрешаю прод» — окно на 20 минут для этого проекта. «Запрещаю прод» — закрыть раньше. Настройки: `.memory/config.json` → `prodGuard` |
| **Бриф с утверждением** | `/orchestra` сохраняет бриф в `.memory/briefs/`. `orchestra-memory brief check` проверяет, что есть все семь разделов и нет TODO. Утверждение привязано к версии файла: изменили бриф — утверждение сброшено. Отметки выполненных подзадач (`- [x]`) не считаются изменением | Пишет «утверждаю». Агент сам утвердить не может: файл утверждений защищён сторожем |
| **Инварианты** | `wiki/INVARIANTS.md` — что не должно стать неправдой никогда. Получает каждый исполнитель; оркестратор и роль `reviewer` проверяют по ним diff | Дописывает свои строки «никогда …» |
| **Роли** | `.claude/agents/`: `scout` (разведка, дешёвая модель, только чтение), `applier` (применить готовый план), `reviewer` (проверка diff). Механическая работа не тратит лимит дорогой модели | После установки ролей — перезапустить `claude` |
| **«Почему» в журнале** | `orchestra-memory log` для feature, fix, change, security, deploy, refactor, removed требует `--why`. Ручная чистка данных без устранения причины — тип `cleanup`, в CHANGELOG не попадает | — |
| **Передача смены** | `session-end`: не больше трёх обязательных пунктов (`--gate`) и ровно одна следующая задача (`--next`). В журнале — чек-лист и «Следующая задача» | — |
| **Отчёт исполнителя** | Четыре части: DONE, WHY, RISKS, VERIFY. «Тесты есть» — не проверка: указывается, что реально запускалось | — |
| **Принципы Карпатого** | Думать до кода (допущения вслух, варианты вместо молчаливого выбора), простота, хирургические правки, работа от проверяемой цели. В правилах проекта, в задании исполнителям и — через диагностику — в `~/.claude/CLAUDE.md` для всех проектов | Ничего; отменить глобальный блок — «Отменить последнее» в диагностике |
| **RTK** | Если установлен [RTK](https://www.rtk-ai.app/), диагностика показывает экономию, а исполнители Orchestra получают его хук | `brew install rtk-ai/tap/rtk && rtk init --global` |
| **Время** | С каждым сообщением агент получает реальное время машины и сколько идёт микросессия | — |

## Установка

На каждом компьютере, где вы работаете с кодом (Mac mini, MacBook), один раз:

```bash
cd ~/путь/к/orchestra
npm install && npm run build
npm link          # команды orchestra-mcp, orchestra-serve и orchestra-memory станут доступны везде
```

**Память заводится сама.** Когда Orchestra впервые обращается к репозиторию или ветке без `.memory/` (запуск из панели, MCP-сессия, инструмент памяти, команда `orchestra-memory`, хук Claude Code, выбор репозитория в панели), она создаёт память без всякого `init`: `.memory/`, wiki, правила в `CLAUDE.md` и `AGENTS.md`, хуки и команду `/orchestra`. Ничего не затирается. Эти файлы сразу уходят одним небольшим коммитом (запуск отказывается стартовать в репозитории с незакоммиченными изменениями); если ваши собственные правки лежат в тех же файлах, коммит не делается. Если у ветки нет памяти, а у `main` или `master` есть, файлы берутся оттуда: так две ветки не создают разные копии и не конфликтуют при слиянии. Выключить: `autoMemory: false` в настройках службы, переменная `ORCHESTRA_NO_AUTOMEMORY` или пустой файл `.orchestra-no-memory` в репозитории.

Вручную (если автосоздание выключено, или чтобы задать имя проекта и язык), один раз в проекте:

```bash
cd ~/Developer/data-c
orchestra-memory init --project "data-c"
git add -A && git commit -m "Память проекта"
```

`init` можно запускать повторно: он ничего не затирает. Он создаёт `.memory/`, журнал и CHANGELOG, дописывает правила в `CLAUDE.md` и `AGENTS.md` (между метками `orchestra-memory`), добавляет хуки в `.claude/settings.json` и включает `.githooks/`. То же самое делает кнопка «Включить память» в Orchestra.

Правила в `CLAUDE.md` и `AGENTS.md` читают Claude Code, Codex и агенты в терминалах Orca, так что они ведут память и без Orchestra.

После клонирования репозитория на другом компьютере нужно один раз выполнить `git config core.hooksPath .githooks` (или снова `orchestra-memory init`): git не переносит эту настройку.

## Команды

```text
orchestra-memory context "задача"        что известно и решено по теме
orchestra-memory search "слова"          поиск по фактам, решениям и логу
orchestra-memory add-fact "текст" --tags a,b --files f
orchestra-memory add-decision --title "…" --decision "…" --why "…" --alt "…"
orchestra-memory log --type fix "описание" --files f
orchestra-memory session-end --summary "…" --done "…" --why "…" --next "…"
orchestra-memory digest                  свежая выжимка по логу
orchestra-memory changelog --draft       что войдёт в CHANGELOG
orchestra-memory changelog --write черновик.md [--release "0.2"]
orchestra-memory status
orchestra-memory push                    память + git push
```

Все команды понимают `--repo <путь>`. Автор определяется сам (claude-code, codex или имя из git), можно задать `--author` или переменную `ORCHESTRA_AUTHOR`.

## Работа в Orchestra

В панели под выбором репозитория есть блок «Память»: сколько фактов и решений, открыта ли сессия, кнопки «Включить память», «Свежая выжимка» и «CHANGELOG этапа». Каждый запуск автоматически ведёт лог: задачи воркеров, слияния с типом (feature, fix, docs…), отказы, ошибки. Оркестратор получает инструменты `memory_search`, `memory_add_fact`, `memory_add_decision` и правило: перед завершением поручить воркеру обновить wiki. После запуска Orchestra коммитит память отдельным коммитом `chore(memory): …`.

Воркеры в память не пишут и хуки не запускают: за них пишет Orchestra, а в worktree изменения памяти не нужны.

MCP-сервер Orchestra (`orchestra-mcp --repo …` и `orchestra-serve` с `?repo=` в адресе) даёт любым агентам инструменты `memory_context`, `memory_search`, `memory_add_fact`, `memory_add_decision`, `memory_log`, `memory_session_end`, `memory_digest`, `memory_fresh_digest`, `changelog_draft` и `changelog_write`.
